# Требования к API

> Контрактов с путями и JSON в ТЗ нет. Здесь только ограничения. Конкретный endpoint появляется заметкой по [[Шаблоны/API-контракт]], когда его реально делают.

## Context

Frontend не считает dashboard. Сервер фильтрует по периоду и отдаёт агрегаты. Объём продаж в seed — 2 000–5 000, это аргумент не тянуть сырые строки на клиент ради KPI.

## Details

Каждый аналитический ответ, который питает экран:

- принимает период так же, как переключатель на UI (пресет или from–to — как решите в контракте, но один смысл на все блоки);
- использует определения из [[Разбор задания/03 Домен/Показатели и статусы]] и закрытые пункты [[Разбор задания/03 Домен/Открытые решения]];
- не требует от клиента догрузки всех `Sale` / `SaleItem`;
- валидирует диапазон (from позже to, пустые даты);
- отдаёт понятную ошибку, по которой UI показывает состояние «ошибка API», а не пустой график.

Блоки экрана, которым нужен свой или общий агрегат: KPI, рейтинг (два режима), динамика, категории и топ продуктов, последние продажи. Можно одним запросом или несколькими. Дробление фиксируется в контракте, когда станет ясно, что так проще грузить состояния по блокам. См. [[Разбор задания/04 Dashboard/Состояния и граничные случаи]]: один блок может быть пустым, остальные нет.

N+1 на списке последних продаж (менеджер, клиент, товары отдельными запросами на каждую строку) — то, что ТЗ называет очевидной проблемой.

Авторизации на маршрутах нет. См. [[Разбор задания/09 Вне scope]].

## Decisions

Список URL намеренно не составлен заранее. Выдуманный контракт в vault разойдётся с кодом в первый же день.
