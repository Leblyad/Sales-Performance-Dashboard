# Архитектурные ограничения

> Маленькая система. Баллов за «40 проектов» не будет, если задача решается проще.

## Context

ТЗ прямо разрешает простой модуль оставить простым. Паттерн добавляется, только когда без него хуже читается конкретная проблема (аналитические выборки, а не «так принято»).

## Details

### Backend

Хотят увидеть:

- понятные REST-контракты;
- разделение ответственности без лишних слоёв;
- эффективный PostgreSQL: связи, типы, индексы по месту, агрегаты, понимание SQL, который генерирует ORM;
- отсутствие очевидных N+1;
- async I/O;
- валидацию входа;
- понятные ошибки API.

Raw SQL или Dapper допустимы для отдельной аналитической выборки, если это проще и быстрее ORM. Выбор нужно уметь объяснить. Пока выбор не сделан — пометка в [[Шаблоны/Решение]], не в этой заметке.

Стек зафиксирован: .NET 8+, ASP.NET Core, EF Core, PostgreSQL. Миграции обязательны.

### Frontend

React + TypeScript. UI-кит, графики, состояние сервера — на выбор (в ТЗ названы как примеры, не как требование: TanStack Query, Zustand / Redux Toolkit, React Hook Form, Tailwind / MUI / Ant Design / shadcn, Framer Motion, любая библиотека графиков).

Страница одна, desktop, около 1440×900. Информативная, с иерархией, не набор демо-компонентов.

### Где считается аналитика

Фильтр периода и KPI считаются на сервере. Frontend показывает ответ API и состояния загрузки. Он не скачивает 2 000–5 000 продаж, чтобы посчитать рейтинг в браузере.

## Decisions

- Микросервисы, Kubernetes, облачный деплой — вне задания. См. [[Разбор задания/09 Вне scope]].
- Backend — один проект `SalesDashboard.Api`: пустые `Domain`, `Dto`, `Services` и пустой `AppDbContext`. Где лежат правила кода: [[20 Кодинг-конвенции/Где лежат правила]].
